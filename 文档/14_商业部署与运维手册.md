# 商业部署与运维手册

首发架构：一台 Linux 应用主机 + 持久本地 SSD + 远程对象存储 + CDN + 独立加密备份。容量按 C25 和压测决定，2 vCPU/4GB 仅起测配置，不保证任意流量。开发在 Windows，不影响 Linux 生产部署。

## 环境与配置

开发、预发布、生产隔离域名、数据库、对象桶、短信模板/限额、支付配置和密钥。预发布只用匿名测试数据，不复制生产手机号与设定图。数据库和密钥不得进入 web/public 或任何静态构建包。

| 配置 | 用途 | 管理要求 |
|---|---|---|
| APP_ENV、PUBLIC_ORIGIN | 模式与可信站点 | 生产启动拒绝 localhost/HTTP 或错误默认值 |
| DATABASE_URL、DATA_DIR | SQLite 路径与数据目录 | 绝对 Linux 路径、持久磁盘、最小文件权限 |
| SESSION/CSRF/OTP 密钥 | 会话与验证码安全 | 独立密钥，安全注入与轮换，不用示例值 |
| PII_ENCRYPTION_KEYS、PHONE_LOOKUP_KEY | 私密信息保护 | 版本管理，轮换时保留必要旧解密能力 |
| SMS_PROVIDER、签名/模板、费用限额 | 手机登录 | 密钥服务器侧，告警和每日预算 |
| PAYMENT_PROVIDER/商户/AppID/证书或公钥 | 支付 | 后台仅显示非敏感状态，不显示私钥 |
| 信用卡渠道（Stripe）：`STRIPE_SECRET_KEY`、`STRIPE_WEBHOOK_SECRET`、`STRIPE_ACCOUNT_ID` | 信用卡收款与回调验签 | 三项缺一即拒绝生产启动；签名密钥按 endpoint 单独签发，轮换时旧密钥保留一个容忍窗口；`STRIPE_API_VERSION` 固定版本避免回调结构漂移 |
| 电子签渠道：`ESIGN_PROVIDER`、`ESIGN_API_BASE`、`ESIGN_APP_ID`、`ESIGN_APP_SECRET`、`ESIGN_WEBHOOK_SECRET` | 合同签署发送与状态回传（C07） | 商业上线**必须**接入真实电子签服务：`disabled`（未接入）与沙箱渠道都会被生产配置校验拒绝；回调地址为 `/api/v1/esign-notifications/{provider}`，回调原文按摘要留证；`ESIGN_LINK_TTL_HOURS` 控制签署链接有效期 |
| STORAGE_PUBLIC/PRIVATE_BUCKET | 文件 | 权限分离，私有桶禁止匿名读 |
| BACKUP_TARGET、BACKUP_KEY | 离机加密备份 | 与主机独立的账户权限，恢复密钥不只在主机上 |
| 功能开关 | 收款、拼手速、兑换等 | 有审计和默认关闭策略，生产禁用 mock provider |

前端 `VITE_*` 会进入浏览器，只能存公开配置，绝不能放短信/支付/API 私钥。启动时检查缺项与不安全组合并 fail closed。

## 发布流程

1. CI 从锁文件安装，执行 lint、类型检查、领域/集成/契约/浏览器测试、依赖/密钥扫描，生成前端静态包和后端镜像/包、SBOM 与版本标识。
2. 在预发布执行迁移、烟雾测试、支付回调与 worker 恢复测试；检查经营信息和素材授权。
3. 生产发布前确认变更窗口、值班负责人、可恢复备份、迁移兼容性和失败回退条件。
4. 单 SQLite 主机使用兼容迁移、短暂停写/滚动应用进程的受控方式；不得让两个不兼容版本同时写库。数据库迁移只运行一次。
5. 静态构建先上传带内容哈希资源，校验成功后原子切换入口。API 健康检查和 worker 租约恢复后，先员工/受邀客户验证，再逐步开放购买。
6. 观察错误率、支付未知单、锁等待、对账差异和短信费用；超过门槛关闭新下单/营销入口，保留查单、售后和回调接收能力。

本架构不采用多台服务器共享 SQLite 的“蓝绿切换”。特性开关可控制开放范围，但所有真实交易必须记入同一权威账本。

## 网络与进程

只向公网开放 80/443，80 跳 HTTPS；API 监听内网/回环地址。SSH 限制管理来源并使用密钥。TLS 自动续期，过期告警；确认全站 HTTPS 后启用合理 HSTS，不盲目给尚未支持 HTTPS 的全部子域启用 includeSubDomains。

API 一个 worker 起步；任务 worker 独立服务，设置重启策略、心跳、任务租约、指数退避、最大次数和死信。多个 worker 即使意外启动，也以数据库 claim 条件保证一条任务只有一个有效租约，但消费者仍必须幂等。

readiness 检查数据库可读写、迁移版本和必要配置，liveness 只检查进程活着；公共探针不暴露路径、版本秘密或数据库细节。严格限制请求体积、超时和上传范围。交易及个人 API 禁止 CDN 缓存；支付通知路由不能被交互验证码拦截。

站点入口：`/admin` 与 `/admin/*` 必须 rewrite 到 `/admin.html`（模板见 `deploy/nginx/starium.conf` 的 `location ^~ /admin`），否则刷新后台子路由会落回前台。Nginx 的 `client_max_body_size 33m` 与应用层 32MiB multipart 上限配套；请求守卫、分档限额、并发闸门与匿名缓存见 `文档/19`，边缘 CDN/WAF 仍是必需层。

## 备份与恢复

SQLite WAL 活跃时禁止只复制 `.db` 文件作为备份。使用 SQLite online backup API 生成一致快照，执行完整性检查后加密上传独立存储；备份数据库与对象存储清单、schema 版本及必要配置引用。对象存储启用版本/生命周期或独立备份，不把数据库备份误认为包含图片。[SQLite WAL 官方说明](https://www.sqlite.org/wal.html)

初始计划：每 15 分钟快照、每天完整校验、每周恢复演练或按确认后的频率执行。若快照时长或文件大小使 15 分钟 RPO 无法达成，则改为经验证的增量复制/备份方案或迁移 PostgreSQL，不继续宣称满足 RPO。保留期见 C22，备份密钥与文件分离保管。

恢复步骤：

1. 关闭新下单和会改变账本的人工操作；保留必要回调的持久接收或让渠道按协议重试，不给未落库通知假成功。
2. 在新目录/新主机验证并解密快照，运行 integrity_check、foreign_key_check、行数与金额/积分总和检查。
3. 恢复对象引用和密钥版本，应用注销/删除墓碑记录，防被删除的私密资料复活。
4. 查询备份时间之后的全部渠道收款/退款与账单，幂等补账；核查库存、名额和积分。
5. 在隔离环境验证用户登录/订单/私密图片/worker，然后切入口、逐步开单；记录丢失窗口和实际 RPO/RTO。

## 回滚

普通应用回滚使用上一稳定包，前提是它兼容当前 schema。数据库已产生新交易时禁止还原旧快照；优先应用回退或正向修复。破坏性迁移应在独立变更窗口完成，先冻结交易并做恢复演练。

支付通知与查单处理必须在降级期间继续可恢复运行。关闭支付入口不等于停止接收已发起订单的付款；仍可能有迟到通知，按 08 处理。

## 指标、告警与值班

| 观察项 | 初始触发条件 | 处置 |
|---|---|---|
| API 错误/可用性 | 5xx >1% 持续 5 分钟或探针连续失败 | 排查/回滚应用，必要时关新订单 |
| 支付未知/通知失败 | UNKNOWN >5 分钟、验签异常突增 | 查单，检查证书/时间同步；不凭人工截图入账 |
| 对账差异 | 任意未解释资金差异 | 财务任务与告警，不能静默忽略 |
| SQLite | busy 超过 0.5% 或 P95 等待>200ms 持续 15 分钟 | 缩短事务/降载/评估迁移 |
| 磁盘 | 使用率≥80% 或异常增长 | 清理非业务临时文件、扩容；禁删 WAL |
| 备份 | 最新可验证备份>30 分钟 | 告警，恢复备份链路，评估暂停新交易 |
| worker | 心跳>2 分钟、死信出现 | 重启/排查，幂等重放 |
| 短信 | 日预算 80% 或发送激增 | 风控、预算熔断，保留异常申诉入口 |
| TLS/支付证书 | 距失效<14 天或轮换失败 | 更新并验签回归 |

告警发给 C21 确认的运营/技术负责人。日志记录 trace_id 和脱敏业务 ID；禁止手机号、地址、验证码、session cookie、设定图 URL 签名和完整支付报文。访问安全日志保留遵守实际法律义务与 C22，不与调试日志混为一谈。

## 运营手册最小流程

发布商品：录入事实 → 上传有授权图片 → 设置 SKU/价格/库存 → 预览 → 发布。报价：检查设定授权和可制造性 → 明细和交期 → 发布版本 → 客户确认。发货：核对已付余额/客户确认 → 包装与物流 → 更新通知。退款：售后审核 → 财务额度校验 → 原路退款 → 查证成功 → 对账。

洗毛：每日查看待处理 cleaning 申请 → 核对期望日期产能 → 批准时给出窗口与报价 → 客户下单后记录收件/到店 → 完成后通知取回或寄回，寄回运费单列。道具与周边：道具与现货共用库存，发布前核对分类（props）与详情页入口，限量或定制必须保留审批，不承诺未测试的承重与发光参数；周边只维护展示内容与图片，不配置售卖、库存扣减或订单入口，未来开放售卖需新的需求确认。

反馈审核：检查有效性 → 理由和等级 → 奖励/不奖励 → 用户通知与申诉。积分纠错必须新增调整流水。员工离职：停用员工账号 → 撤销会话/权限 → 更换其可能接触的秘密 → 检查分配任务。事故记录包含时间线、影响订单、恢复动作、资金核对、用户沟通负责人和防复发改动。
