### 本轮修复的真实缺陷（均有测试或脚本证据）

1. **ORM 主键默认值不可用**：`PkMixin.id` 用 `lambda: new_id(self.id_kind)`，`self` 解析到混入类作用域，任何写入都抛 `NameError`。改用 `declared_attr` 在子类上生成闭包。
2. **库存原子更新被静默抵消（严重）**：`catalog.reserve/release/consume/restock` 的条件 UPDATE 之后没有过期 ORM 缓存，同一事务内的后续 `flush()` 会把旧 `reserved`/`stock_on_hand` 写回，导致“隔一次成功一次”的超卖窗口。修复后四个函数都会 `session.expire(sku)`。
3. **迟到收款被静默吞掉（严重）**：订单取消时应付项已被置为 `CLOSED`，`on_installment_paid` 的条件 UPDATE（只匹配 `DUE/PAYING/CLOSING`）不命中，于是函数在 `already_paid` 分支直接返回——既没记迟到收款，也没写审计，而库存早已释放。现已在 `order.status == "CANCELLED" and installment.status == "CLOSED"` 时置 `late_payment=True` 并写 `order.late_payment_recorded` 审计（08 文档第 23 行）。
4. **后台 API 缺口**：`commissions`、`commerce`、`payments`、`loyalty`、`feedback` 五个模块缺少 `admin_router` 导出，后台挂载时被跳过（运营无法发布报价、发货、退款、审核反馈、调整积分）。已补齐 56 个后台端点。
5. **测试夹具缺少来源校验头**：共用的 `client` 夹具没有 `Origin`，所有写操作被 `CSRF_INVALID` 挡下（表现为大批用例失败）。已在夹具统一设置受信 Origin。
6. **后台路由路径错误**：`admin-router.ts` 的登录路由写成相对 `"login"`（vue-router 直接抛错），父级 path 为空导致 `/admin/dashboard` 匹配不到；对话框断言未考虑 `<Teleport>`。均已修复。
7. **`content.repository` 缺少 `new_id` 导入**：预渲染任务登记路径会在运行时抛 `NameError`（ruff F821 发现）。
8. **敏感动作缺少服务端验证（安全）**：`POST /me/sensitive-verify` 原来不校验验证码就标记会话已验证。现要求 `purpose=sensitive_action` 的挑战 + 服务端 HMAC 校验，且只标记当前会话、不签发新会话。
9. **询价页死控件与上传流程重复实现**：步骤条向前点击无效；询价页自己重写了一份上传流程而非复用共用 `runUploadFlow`。已修复（前端测试从 21 个失败降到 0）。
10. **关单丢弃渠道关闭结果（竞态）**：`cancel_order` 调用 `close_payment_attempts_for_installment` 时丢弃返回值，渠道回「已支付」或关闭失败时不会拦截，仅靠随后读 `paid_cents` 兜底；而库存此时正要被释放。已新增支付端口 `unresolved_attempt_count`，在释放预留前检查是否仍有活动支付尝试，有则抛 `PAYMENT_UNKNOWN` 拒绝关单（fail closed）。
11. **测试隔离性丢失（工具/环境）**：`conftest._TempDirFactory.mktemp` 用 `tempfile.mkdtemp` 创建 0700 目录，受限沙箱下 SQLite 文件建不了，`_file_database_usable()` 返回 False 后整体退回**固定名共享内存库**，用例互相污染，导致同一份代码出现「6 failed」与「5 failed」两种结果。已改为 `mkdir` + 随机名。
12. **Windows 缺 IANA 时区库**：`ZoneInfo("Asia/Shanghai")` 在无系统时区库的 Windows 上直接抛 `ZoneInfoNotFoundError`，导致后端整体无法导入。已在 `pyproject.toml` 加 `tzdata; sys_platform == 'win32'`。
13. **worker 调用不存在的函数名**：`app/worker.py` 的到期订单扫描写的是 `commerce_service.close_expired_orders`，商务模块实际导出的是 `expire_due_orders`（端口同名）。已改为通过 `commerce.ports.expire_due_orders` 调用，符合“跨模块只用公开端口”的约束；已实测 `run_once()` 一轮与处理器直接调用均正常返回（`closed:0`，当前无到期订单）。

## 2026-09-18 / 修复第 9 轮：R21 跨境可见性、发票闭环、退款按行分摊（本轮）

日期/版本：2026-09-18；工作树（`273a8cc` 之后的增量）。

增量/任务 ID：R21（完成本地可验证部分）。已实现的 FR：FR-011/FR-013（结算金额与运费由服务端裁定）、FR-022（账户与后台页面的状态完整性）；C02/C24（简中+英文、CNY+USD 双区）、C16/C17（售后与运费政策可配置、跨境说明）。

**发现并修掉的三个真实缺陷**

1. **开票开关永远读不到（关不掉）**：`commerce.service.request_invoice()` 从 `policy["invoice"]["invoice_enabled"]` 读开关，而校验模型 `CommercePolicy` 与后台接口写的都是**顶层** `invoice_enabled`，`Invoice` 子模型还禁止额外字段。结果是：运营在后台把开票关掉，客户仍然可以提交开票申请（默认值 `True` 兜底），而写入 `invoice` 子块的旧测试夹具属于后台根本产生不了的形状——测试"通过"掩盖了缺陷。
2. **跨境比例没有任何配置入口**：`CommercePolicy` 没有 `cross_border` 块，运营提交即被 `extra="forbid"` 整次拒绝；同时 `preview_checkout()` 的返回是**显式白名单字典**，即使服务端算出了跨境字段也会在预览响应里丢掉（本轮先加了 DTO 字段，测试立刻暴露了这个丢字段问题）。
3. **后台设置改不了嵌套政策**：经营设置页只把设置值当标量提交（`String(value)` → `"[object Object]"`），而 `commerce.policy` 是嵌套对象，运费、售后、发票、跨境政策因此**在后台完全无法修改**；表格与分组概览也把对象渲染成 `[object Object]`。
