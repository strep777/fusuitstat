## 3. 已复现的代码缺陷

P1 表示上线前必须修复；P2 表示影响功能或工程验收。

### BUG-01 / P1：未分配装师可读取其他制作单

- 位置：`server/app/modules/commissions/admin_router.py:475`、`:500`；序列化位于 `service.py:2588`。
- 依据：SRS 角色边界、07/10 的私密量体规则、TC-A04/A05。装师只能查看分配给自己的制作单。
- 复现：创建客户制作单，再以未分配到该单的 maker 账号完成真实密码与 MFA 登录，请求 `/api/v1/admin/commission-projects/{id}`。
- 预期：403 或 404；实际：200。
- 原因：接口只检查 `production.read`，直接按 ID 取单，随后以 `include_private=True` 序列化；列表的 `maker_id` 也由请求参数控制。详情若有量体记录，将进入解密序列化路径；本轮动态用例验证的是未授权详情读取，没有额外创建量体记录。
- 修复：在服务端统一落实装师数据范围；详情、列表、更新和阶段附件应共用对象授权。复核 `production.write` 与重新分派权限，避免读接口修好而写接口仍越界。
- 验收：未分配装师读写均拒绝；分配装师只访问本人任务；运营全量权限单独验证。

### BUG-02 / P1：在线支付关闭后仍可创建支付

- 位置：`server/app/modules/payments/router.py:66`、`service.py:286`。
- 依据：AGENTS 第 11 条、功能开关默认关闭要求。
- 复现：确认服务端 `feature_flags(...)["online_payment"] == False`，通过客户会话、CSRF、幂等键调用创建支付接口。
- 预期：403 / `FEATURE_DISABLED`；实际：201，生成沙盒支付尝试。
- 原因：创建链路检查渠道配置，但没有检查业务功能开关。渠道是否配置与是否允许新支付是两个条件。
- 修复：新建支付入口统一检查业务开关；关闭新支付后，历史查单、回调、退款仍应能够处理。

### BUG-03 / P1：生产配置遗漏沙盒支付别名

- 位置：`server/app/platform/config.py:173`；`server/app/adapters/payments/__init__.py` 的 `SANDBOX_PROVIDERS` 与工厂。
- 依据：生产禁止沙盒冒充真实收款。
- 复现：构造其余安全字段满足校验的 production Settings，令 `PAYMENT_PROVIDERS=sandbox`。
- 预期：配置校验失败；实际：创建成功。校验只拒绝 `mock`，工厂却把 `mock` 和 `sandbox` 都视作沙盒。
- 影响：生产启动门禁可能放行沙盒配置。本轮没有启动生产服务或伪造真实交易，不能据此宣称已证明真实资金入账可被攻击。
- 修复：统一适配器分类，在配置和适配器工厂两层拒绝所有生产沙盒别名；增加大小写、混合渠道、别名回归。

### BUG-04 / P1：关闭优惠券仍会应用内置券码

- 位置：`server/app/modules/commerce/service.py:72`、`:102`、`:142`，结算计价调用同一函数。
- 依据：C16 要求按工作室配置执行；AGENTS 要求开关关闭时后端拒绝。
- 复现：优惠券开关 false、无运营券配置时，计价传入 `NEIXING10`，商品金额 10000 分。
- 预期：不应用优惠，接口应按未启用拒绝；实际：默认策略直接优惠 1000 分。
- 原因：默认业务策略内置真实可用券码，计价不读开关，且后台券配置与默认券合并。
- 修复：生产默认券集合为空；结算预览与正式建单均检查开关及券资格，不把测试券写入业务默认值。
- 证据层级：本轮动态验证到业务计价函数；未额外跑完整优惠下单 HTTP 流程。

### BUG-05 / P1：业务通知只生成站内记录，没有邮件投递

- 位置：`server/app/modules/commissions/ports.py:102`；`notifications/service.py:32`、`:52`；`notifications/ports.py:23`。
- 依据：C27 已确定邮件必选并取代独立站内信，C07 合同链接通过邮件发送。
- 复现：委托通知端口登记 `quote.published`，传入用户及含测试邮箱的 payload。
- 预期：创建邮件投递记录；实际：Notification 为 1 条、Delivery 为 0 条。
- 原因：业务端口未填写 `email_target`，通知服务也没有按用户解析收件人，直接跳过无目标渠道。客户 User 模型未提供邮箱字段；员工邮箱不能替代客户收件地址。重试 worker 无法补发从未登记的邮件。
- 修复：完成客户邮箱采集与验证、通知目标解析、交易邮件登记及失败重试；合同邮件复用同一流程。不能仅配置 SMTP 就宣布完成 C27。

### BUG-06 / P2：后台规则值缺乏按字段校验

- 位置：`server/app/modules/content/service.py:434`、`:571`；`content/schemas.py` 的 `SettingUpdateInput`。
- 复现：更新 `commission.policy`，写入 `prepayment_percent="invalid"`。
- 预期：写入时返回可解释字段错误；实际：未抛 AppError，非法值被接受。读取策略又直接执行 `int(...)`，该值会导致 ValueError。
- 影响：合法运营账号误填配置后，使用该规则的展示与业务路径可能失败；比例、时长、积分分母等边界也缺少统一校验。
- 修复：按设置 key 绑定类型明确的配置模型，先验证再持久化；同时验证比例范围、正数期限、积分分母和布尔类型。禁止把字符串 `"false"` 当真值处理。
